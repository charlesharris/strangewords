<objective>
Ship the robot poet on the server: a user who opted in (allowBot true on POST /v1/enter) and finds no human within a [TUNABLE] window (25s) is paired with the robot poet, which then writes its lines from server/internal/poet, and every view of that session says so (partnerIsBot). Nobody else is ever paired with it.

Locked decisions implemented here: D-01 strict opt-in, default OFF (absent/false/malformed flag means humans only); D-03 human first, robot poet only after the window, overlapping opted-in humans pair with each other; D-04 disclosure computed server-side for the whole session; D-05 lines from server/internal/poet, no external AI. CONTEXT.md numbers these decisions 1 to 5, cited here as D-01 to D-05. D-02 (settings UI) is in Plans 02 (persisted preference) and 03 (gear and sheet).

Mechanism (RESEARCH option (c′), the planner's discretionary call): server-side and driven by polls. The waiter's own GET /v1/waiting claims itself out of the queue with LREM once the window has passed. The bot is a flagged participant created pre-dismissed, never a queue member. Its lines are produced lazily on the human's polls by replaying a session-seeded poet. There is no worker, no second queue, no lock and no new Redis key.

Purpose: the backend half of the phase goal, and the phase's tracer. Task 1 proves the riskiest architecture (atomic claim plus structural segregation plus disclosure) end to end over HTTP and Redis before anything expands.
Output: botplayer package, extended config/sessions/store/matchmaker/metrics/gateway, and bot_test.go proving the invariants.

Scope note: per the user's mid-planning scope directive (minimal shippable feature), the moderation-report BotPartner field, the privacy.html on-device line, the cmd/bot dev-only comment and standalone store/sessions unit-test files are not in this plan. The gateway tests cover the claim and disclosure end to end. See the Source Coverage Audit.
</objective>

<assumption_delta_decision>
primary_noun: participant. Before this phase every participant was an anonymous human. Now a participant is a human or the robot poet.
decision: add-alongside. Participant gains `Bot bool` (json bot,omitempty) next to the existing fields, and View gains a single `PartnerIsBot bool`.
rationale: every index-based path (TurnPolicy authorship, ViewFor, dismiss-all-to-dissolve, DeleteSession) keeps working unchanged for a pre-dismissed, tokenless bot participant. A participant-kind enum would touch every consumer for one new kind.
accepted_debt: a third kind (a moderator, a second bot persona) or N>2 sessions with mixed partners would need a `Kind` enum on Participant and a per-participant kinds list on View in place of the single PartnerIsBot bool. iOS (Plan 02) mirrors the same single flag, so that promotion would be a coordinated wire change.
</assumption_delta_decision>
