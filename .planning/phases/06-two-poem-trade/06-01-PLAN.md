<objective>
Ship the server half of the two-poem trade. After poem 1's reveal either participant may call POST /v1/session/{id}/trade. Offer and acceptance are the same signal, and when every participant has asked, poem 2 begins in the same session with the start role swapped. The robot poet accepts on its own after its think time and writes poem 2 from a per-poem deterministic replay. Declining, leaving or letting the reveal lapse dissolves exactly as today.

Locked decisions implemented here (06-CONTEXT.md):
- D-01: each poem keeps its own reveal. Poem 2's reveal has no further trade (MaxPoems = 2), and the existing reveal rhythm is doubled, not replaced.
- D-02: the trade is offered, never automatic. Poem 2 begins only when both have asked. Letting go closes the trade, and an unanswered offer ages out under the existing RevealTTL, with no new timer.
- D-03: roles swap. The start offset for poem N is StartIndex + (N-1), computed in Session.AuthorOf. StartIndex stays an untouched encounter-level field and the turn policy is unchanged.
- D-06: the robot poet trades too. Its acceptance is poll-settled through the same WATCH/MULTI compare-and-set as its lines and is armed with BotThink, so it is never instant.

D-04 and D-05 are client-only and live in Plans 02 and 03.

Orchestrator defaults honored:
- No push for the offer.
- No new timer: the offer rides RevealTTL, and the trade returns to SessionTTL.
- Zero new sw: key classes, and all trade state lives inside the session blob.
- Old clients are fail-safe: a client that never calls /trade can never be pulled into poem 2.

Discretion calls (reversible, recorded):
- Offer and accept share one endpoint and one per-participant flag (WantsTrade), mirroring the symmetric Dismissed flag.
- The role swap derives from PoemCount rather than mutating StartIndex. StartIndex keeps its encounter-level meaning, the swap is N-ready, and Phase 5's tests that force StartIndex keep their poem-1 meaning.
- Poem 2's robot-poet seed is FNV-1a over the session id plus the poem number, so it differs from poem 1. Poem 1 keeps Seed(id), which keeps the existing determinism and the cmd/bot seedFor lockstep. The poet doc says "Make one per poem with New".
- Poem 1's cached line responses are purged when poem 2 begins, so privacy.html's "erased with the poem" stays true. The IdemKeys teardown list keeps every key, so a failed purge is still caught at dissolution.
- handleDismiss moves onto the compare-and-set. A stale plain write could otherwise revert a just-begun poem 2 to poem 1's reveal. Its one behavior change (a single dismiss during an active poem 2 dissolves) and its one preserved path (an active poem 1 keeps HEAD's all-must-dismiss rule) are recorded as decision DEC-06-01 in Task 3.
- cmd/bot is unchanged. It is the dev "robot poet friend" client, and dismissing at the reveal is D-02's decline path.
- No push nudge when poem 2 begins: the push notifier is stubbed and the orchestrator default says no push.

Purpose: this plan proves the wire contract that Plan 02 mirrors on iOS: route, request, View keys and error codes.
Output: the domain trade state, the /trade endpoint, the robot poet's acceptance, a CAS-safe dismiss, trade metrics, a privacy page update, and Go tests under the miniredis + fake-clock rig.

<assumption_delta_decision>
Pluralization: a session goes from exactly one poem to up to MaxPoems (2) sequential poems in one encounter.
Decision: no-change (no poems[] collection is added, and no second set of poem fields sits alongside the first).
Rationale: the encounter is already the primary entity. session.go splits encounter-level fields (ID, Participants, StartIndex, Bucket, CreatedAt) from poem-level ones, per plan.v1.md §6 and §13's "continue with this person" design. Poems are strictly sequential, so there is only ever one live poem per session, and BeginNextPoem resets the poem-level fields in place. A poems[] history would keep finished poems on the server, which breaks the ephemerality promise and privacy.html. Two bookkeeping fields move from the poem-level block to the encounter-level block of the struct with no JSON tag change. PoemCount is the encounter's poem ordinal. IdemKeys is the teardown list, which spans every poem. The struct comment "v1 has exactly one poem" is rewritten to describe the trade.
</assumption_delta_decision>
